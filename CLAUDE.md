# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Privacy-first, fully local expense tracker. Bank statements (PDF/CSV) are parsed into transactions by a local LLM served by **Ollama**, stored in SQLite, and viewed through either a FastAPI + HTMX web UI or a Textual terminal UI.

`app_spec.md` (v2) is the full specification, written for readers new to the app, and the code implements all of it. It covers config (§1.4), the schema and statement lifecycle (§2), ingestion and review (§3), the validator (§4), dedup ids (§5), rules (§6), both UIs (§7), analytics (§8) and privacy rules (§9). Appendix A.1 is the history of the original gap list, and code and tests still cite its item numbers. A.2 lists the known limitations, which are accepted behaviour rather than bugs. Appendix B is the v1→v2 DB migration. Code comments cite spec sections (`app_spec.md §3.2`), so keep the section numbers stable. When you change behaviour, update the spec in the same change: a new limitation goes in A.2, and the README if users would notice. This file is the developer's view of the same code.

## Commands

All commands run from the repo root — modules use absolute imports (`from core...`), so there is no package install step.

```bash
pip install -r requirements.txt     # Python 3.11+

python run_web.py                   # Web UI on [web] host:port from config.toml (default http://127.0.0.1:8000)
python run_web.py --dev             # same, with auto-reload
python -m tui.app                   # Terminal UI: d/t/q screens, ←/→ month, PgUp/PgDn page, / search (Esc clears), a account, c category, x transfer, r refresh

# Tests (stdlib unittest; pytest is not in requirements)
python -m unittest discover tests     # tests set EXPENSE_TRACKER_DB to a temp file; never the real DB
python -m unittest tests.test_ollama_status.TestWebOllamaStatusRendering.test_api_status_endpoint_online
```

Real ingestion of PDFs and unmapped CSVs needs `ollama serve` running on `localhost:11434` with a model pulled (default `llama3.1`); a CSV with a saved mapping needs no Ollama. Importing `web.app` calls `db.init_db()`, so every test module must set `EXPENSE_TRACKER_DB` **before** importing `core` or `web`. Copy the guard block at the top of the existing test files, or a test run will migrate your real DB. Tests must never reach a real Ollama: patch `web.app.list_available_models` / `web.app.is_ollama_available` in any test that renders `/upload`, and `core.ingestion.extract_transactions` / `extract_statement_metadata` in any test that runs a job.

No linter or formatter is configured.

## Architecture

Three layers: `core/` holds all logic and data access; `web/` and `tui/` are thin front-ends that call `core` directly. There is no service layer or API between them, and both UIs share the same SQLite file.

**Ingestion pipeline** (spec §3): nothing reaches `transactions` without the user committing it.
1. `POST /upload` (`web/app.py`) streams the file into `jobs.tmp_dir()` under a generated name (a private `tmp/` next to the DB) and hashes it while writing. The client filename is display text only (`_sanitize_filename`). Only `.pdf` and `.csv` are accepted, up to 20 MB. The account comes from the form (`_resolve_account`): a new account name wins, then the selected id, and with neither the `Default` account is used. A **CSV** is checked against the account's `csv_mappings` (`csv_import.find_mapping`, by header signature). With no match, the route returns `partials/csv_mapping.html` and the file stays in `tmp/`. Its generated name is the form's `token`, validated by `_held_csv` so that it can never name another path. `POST /upload/csv-mapping` then saves a mapping, picks the LLM, refreshes for another header row, or cancels (which deletes the file). Ollama availability is checked only when the LLM will be used. Next comes `staging.create_import` (`extractor` is `llm` or `csv_mapping`), which creates a `queued` statement; re-uploading the same bytes to the same account raises `AlreadyImported`. Finally `jobs.submit` runs, and the route returns `partials/import_status.html`, which polls `GET /imports/{id}/status` every second.
2. `core/jobs.py` runs one worker thread. A job with a `mapping` is parsed by `csv_import.parse_file`, with no LLM; rows that don't parse are kept for review to flag. Otherwise `run_job` calls `ingestion.read_pages`, which picks the parser by the extension of `source_name`, and **deletes the file right after**. Then `ingestion.extract_statement` runs and finally `staging.stage_rows`, ending in `review` or `failed`. A locked PDF raises `PasswordRequired`, and the job is parked in `needs_password`: the job and its file are held in `jobs._held` until `provide_password` (`POST /imports/{id}/password`) or `cancel`. The password lives only on the in-memory `Job` (`repr=False`) and must never reach logs, `statements.error` or disk. `jobs.start()` (called once when `web.app` is imported) marks `queued`/`needs_password`/`extracting` jobs `failed: interrupted` and wipes `tmp/`. Only the web server may call it; the TUI must not.
3. `extract_statement`: `_chunk_pages` packs whole pages into chunks of up to `CHUNK_SIZE=6000` chars, splits only on line boundaries, and repeats the CSV header in every chunk. Chunks **must not overlap**, because overlap re-emits rows that §5 dedup keeps as genuine repeats. Each chunk goes to `ollama_client.extract_transactions` (`format=` the Pydantic schema, `temperature=0`). A failing chunk is recorded and the rest continue. The first and last chunks are also asked for the period and balances (`extract_statement_metadata`), and a failure there is non-fatal.
4. `core/staging.py`: `stage_rows` stores rows in document order and runs `_revalidate`, which uses `core/validator.py` (pure §4 checks) plus `duplicate_in_ledger` (ids computed exactly as commit will) and reconciliation. The source text is used once for `not_in_source` and never stored. Review edits (`update_row`, `set_dropped`, `update_metadata`) revalidate the whole statement. `commit` refuses rows with errors, and refuses a balance mismatch unless `accept_mismatch` is set. It then inserts with §5 ids, deletes the staged rows and runs the rules engine, all in one transaction. All status-checked writes use `_write_tx` (`BEGIN IMMEDIATE`).
5. The id is `models.compute_transaction_id`: `sha256(account_id|date|normalized desc|amount_minor|ordinal)`, where the ordinal counts identical rows within one statement (spec §5). Insert a **whole statement** per call, because ordinals restart on every call. Changing the formula requires a migration that recomputes every id. `database.import_statement` writes straight to the ledger, bypassing review, and is used only by tests.

**Ledger editing** (`/transactions`, `/imports`): each transaction row is `partials/tx_row.html`. Edit swaps in `partials/tx_row_edit.html`; Save, Reset and Cancel swap the row back via `hx-target="closest tr"`. Delete returns an empty 200 body, so HTMX removes the row. A save goes through `database.set_manual_category`, which makes the row `manual`; `reset_to_rules` undoes that and re-runs the engine. The list's pagination links reuse the route's `filter_qs`, so any new filter must be added to the `filters` dict in `transactions_page`, not to the template. `staging.delete_import` deletes a statement, and `ON DELETE CASCADE` removes its transactions and staged rows. It refuses while the job is running. `analytics.get_uncategorized_count(year, month)` and the list's `uncategorized=1` filter must stay the same definition (non-transfer rows in `Uncategorized`).

The review UI (`/imports/{id}`) shows the live `import_status.html` while a job is queued, extracting or waiting for a password. Otherwise it re-renders `partials/review_body.html` after every action, because one edit can change other rows' duplicate flags and the reconciliation. Row Save buttons post their row's inputs with `hx-include="closest tr"`. Templates format money with the `money` and `major` filters (integer minor units in, string out).

**Configuration** (`core/config.py`, spec §1.4): `get_config()` loads `config.toml` once (git-ignored; see `config.example.toml`) or the file named by `EXPENSE_TRACKER_CONFIG`. Never hardcode the LLM host or model, the currency, the DB path or the web host/port; read them from config. Format money with `models.format_money` (both UIs) or the Jinja filters `money` (minor units), `currency` (major-unit floats) and `major` (editable input). Templates get `config` from the context processor, and `base.html` shows a warning banner when `config.llm_is_local` is false. Tests that need other settings patch `get_config` in the module under test (e.g. `web.app.get_config`, `core.ollama_client.get_config`); `get_config` is `lru_cache`d, so setting env vars after import has no effect.

**LLM calls** (`core/ollama_client.py`): every call goes through `_chat`, which uses `ollama.Client(host=..., timeout=chunk_timeout_s)` with `format=` the Pydantic schema and `temperature=0`. Output schemas live **only** in `core/models.py`, and prompts must not restate them. Invalid output is retried `max_retries` times and then raises `OutputInvalid`; a timeout raises `ExtractionTimeout` and is not retried. Exception messages and INFO+ logs must never include model output or statement text (spec §9.5), because they end up in `statements.error`.

**Database** (`core/database.py`, `core/migrations.py`): there is no ORM. The schema is spec §2 (v2), versioned with `PRAGMA user_version`. `init_db()` calls `migrations.migrate()` on every startup. It creates v2 on an empty file, or migrates a v0/v1 file per spec Appendix B (backup to `expenses.db.v1.bak`, one transaction that rolls back on failure). DDL runs statement by statement inside an explicit `BEGIN` (never `executescript`, which commits). All connections, including analytics, go through `database.connect()` (WAL, foreign keys, `busy_timeout=5000`), and every function accepts a `db_path` override. The default is `data/expenses.db`, or the `EXPENSE_TRACKER_DB` env var when set. Money is integer `amount_minor` (paise), and `models.to_minor` / `from_minor` are the only conversions. `TransactionRecord.amount` is a display-only property, so never sum it. Queries join `statements` to expose `source_file`. Dates are `YYYY-MM-DD` text, and month filtering uses `LIKE 'YYYY-MM-%'`. Amounts are negative for money out, and analytics excludes `is_transfer = 1` rows.

**Category rules** (spec §6, `database._run_rules_engine`): rules match on a Python `casefold()` substring of `raw_description`, never SQL `LIKE`, so `%` and `_` are literal. A rule can be scoped by `account_id`. For each non-`manual` row, the highest `priority` wins, with ties going to the lowest id. The engine sets `category`, `cleaned_merchant`, `rule_id` and `category_source='rule'`, and sets `is_transfer=1` for `mark_transfer` rules but never clears it. When a row's rule no longer matches, the row reverts to `Uncategorized`/`default`. Patterns are unique, and `database.upsert_rule` updates the existing rule on a pattern clash; that is the only way to edit a rule. A blank pattern never matches. `categorizer.add_rule` and `remove_rule` re-run the engine. `count_rule_matches` uses the same matching for previews.

**Web UI** (`web/app.py`): server-rendered Jinja2 templates with HTMX. POST/DELETE routes return fragments from `templates/partials/` rather than full pages, so new interactive features should follow that pattern. A Jinja `context_processors` hook injects `ollama_status` into every template (it drives the status badge in `base.html`). `is_ollama_available()` caches its result for 3 seconds, and `/api/ollama-status` bypasses the cache with `force=True`. Charts are hand-rolled SVG in `web/static/charts.js` with no JS dependencies. Static assets are local only (HTMX is vendored at `web/static/htmx.min.js`, with no remote fonts or CDNs); `tests/test_appendix_a_fixes.py` enforces this. Query params never cause a 500. On the dashboard an invalid year or month falls back to the current month; on the transactions list an invalid month is dropped from the filter. Both take an `account_id` filter, validated by `_account_param` (blank or unknown means all accounts). `/accounts` has account CRUD (`database.create_account` / `update_account` / `delete_account`, which raise `AccountError` with a user-facing message) and lists the saved CSV mappings. The rules form posts `priority`, `mark_transfer` and `account_id`, and `GET /rules/match-count` gives the live count.

**TUI** (`tui/`, spec §7.2): a Textual app with `DashboardScreen` and `TransactionsScreen`, which call `core.analytics` / `core.database` directly. Styling lives in `tui/style.tcss`.
* **Shared state:** the selected month (`app.year`, `app.month`), `app.account_id` (None = all) and `app.db_path` (tests pass a temp DB) live on `ExpenseTrackerTUI`. Screens read them in their refresh method, which runs on mount and on `on_screen_resume`.
* **Binding rules:** app keys (`d`/`t`/`q`) must **not** be `priority`, or they would steal letters typed into `PromptScreen` (the modal used for search and category entry). Screen keys that `DataTable` also binds (←/→/PgUp/PgDn) **must** be `priority`, or the focused table swallows them.
* **Edits:** they go through `set_manual_category`, like the web UI. The TUI never starts ingestion jobs and must not call `jobs.start()`.
* **Tests:** `tests/test_tui.py` drives it with `App.run_test()` / Pilot.

`data/` is gitignored and created automatically. `uploads/` is no longer written to (statements aren't retained); any files left there from earlier versions can be deleted.
